## 1. 覆盖范围

管理后台与 RBAC 纳入 P0。用户端继续支持 Flutter Windows/Web/Android；管理端优先交付 Flutter Web 的独立入口与布局，复用 Dart API 模型、认证与权限组件。两个界面使用同一套 Haruka 用户身份与权限系统，但会话标记 client/admin 受众并分别校验；管理端入口不会因为已经登录用户端就自动放行。

本项目的完整 RBAC 覆盖用户、多角色、角色权限配置、角色继承、授权/撤销、允许/拒绝规则、两端页面/菜单/按钮、后端接口、数据范围、权限刷新与审计。不以固定的 is_admin 字段或“前端隐藏菜单”代替授权。

| 控制层 | 要控制的事项 | 最终执行位置 |
| --- | --- | --- |
| 登录 | 账号状态、用户端登录资格、管理端登录资格、会话有效性 | 认证服务 + 授权服务 |
| 用户端显示 | 书库/阅读、试卷、收藏、练习、Agent、设置等页面、功能入口、按钮和只读状态 | Flutter 权限快照、路由守卫、组件守卫 |
| 管理端显示 | 管理菜单、页面、列表字段、操作按钮与编辑能力 | Flutter Web 管理布局与同一权限契约 |
| 业务操作 | 读/写/删除、上传/导出、生成/批改、任务重试等 | FastAPI + 服务层 + Worker/Agent |
| 数据范围 | 本人学习数据、平台运维元数据、敏感字段的可见范围 | 授权结果 + 仓储过滤 + DTO 字段白名单 |

采用默认拒绝，每个请求都检查权限，且资源归属仍单独校验。这符合 [OWASP 授权建议](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)。

## 2. 后台功能与角色

### 管理功能

| 模块 | 首版能力 | 边界 |
| --- | --- | --- |
| 运维概览 | 用户/存储/任务/AI 用量与失败摘要，受权限控制的管理首页 | 只呈现授权的聚合或运维字段 |
| 用户管理 | 查询账号、创建/审批/启停账号、分配角色、查看登录状态、撤销指定/全部会话 | 创建/改角色/禁用/撤销分别授权，不能读取密码或个人 Key |
| 角色与权限 | 自定义角色、多角色分配、角色继承、授权/拒绝矩阵、影响预览、有效权限查询 | 权限代码由后端注册；编辑角色权限不等于可新增任意可执行接口 |
| 两端菜单 | 分别维护用户端/管理端的菜单分组、标题、顺序、显示开关及所需权限 | 路由/组件键来自发布版本允许清单，不能配置任意代码或外部脚本 |
| 登录与注册策略 | 开放/关闭注册、是否需审批、注册默认角色；账号与会话治理 | 邮箱验证/找回邮件能力仍待明确；注册开关不等同于现有用户禁用 |
| 配额与模型目录 | 配置可用功能、供应商/模型能力目录、用户/全局配额 | 不新增共享付费 Key，不读取或替用户填写个人 Key |
| 资料/试卷与任务运维 | 查看所有者引用、格式、容量、解析/批改状态、失败类别；取消任务和恢复允许的非付费阶段 | 默认不提供他人原文、答卷、成绩正文；重试付费步骤仍需原用户当前权限与授权 |
| 审计与日志 | 查询权限/账号/管理操作审计；查询经授权裁剪的 Haruka 诊断摘要 | Grafana 保持独立运维认证，不能凭菜单权限获得共享 Loki 全量访问 |

个人材料、答案和模型 Key 的既有隔离继续生效。管理角色可以获得平台运维元数据范围，但不能通过普通用户接口指定其他 user_id 变成他人；管理端操作必须走单独授权的管理服务/DTO。原始私有内容查看、代登录和代用户付费调用不作为后台默认能力。

### 内置角色模板

以下为推荐初始模板；日常业务判断只检查权限代码，不硬编码角色名称。

| 角色 | 初始权限范围 |
| --- | --- |
| learner | 用户端登录及本人学习功能；注册默认角色的推荐值 |
| client_readonly | 用户端登录、本人已有资料/成绩只读；不含导入、删除、生成、批改、导入 CSV 等写/付费操作 |
| operator | 管理端登录、平台状态/任务元数据和明确的运维动作；无角色授权能力 |
| account_admin | 管理端登录、账号管理和限定角色分配；无系统策略/超级管理员管理能力 |
| security_admin | 管理端登录、允许范围内的角色/权限/菜单维护；授权受授予上限约束 |
| auditor | 管理端登录、管理审计/诊断只读，无修改权限 |
| super_admin | 系统管理权限与受保护角色维护；仍受身份、状态、归属和不可暴露秘密等硬约束 |

多个角色可组合。管理角色不自动继承 learner 或用户端登录资格；需要同时使用学习端时显式分配。禁用账号、待审批和暂时锁定是账号状态，不用“封禁角色”代替。

## 3. 权限模型与决策语义

权限代码使用稳定的 surface.resource.action 形式；surface 为 client/admin，resource 可用点分子命名空间。新权限随代码和迁移注册到 PermissionCatalog，后台配置授权、拒绝、启停和显示元数据；不允许普通管理表单凭空创造后端没有实现的权限或修改安全 matcher。

一次访问允许的条件为：身份/会话有效 ∧ 账号 active ∧ 当前受众登录权限 ∧ 所需权限允许 ∧ 功能启用 ∧ 数据范围匹配 ∧ 业务状态允许。登录请求先验证凭据，再判断该受众登录权限；不能为尚未登录的请求假定已有会话。

角色可继承角色；继承图必须无环、限制深度并验证所有引用。允许权限取有效角色与继承角色的并集，任何匹配的显式拒绝优先，未知/停用权限默认拒绝。修改继承、父角色停用或权限停用必须重新计算受影响用户；禁用角色不贡献授权，不通过它继续继承父角色。UI 展示直接/继承授权与拒绝来源，避免只显示勾选框造成误判。

不引入任意用户散落的临时权限补丁：用户通过角色获得权限，特例建立可审计角色。受保护账号/角色/权限不可通过普通配置绕过。首版不开放通配符权限字符串的自由输入；超级管理员模板引用明确权限目录，新权限通过受审计发布同步。

### 权限与数据范围

角色授权项绑定 permission_code、effect 与 data_scope，scope 是该权限允许的服务端枚举，不能提交任意 SQL 条件。首版为 self（本人业务数据）及 platform_metadata（管理所需的平台字段/操作范围）。没有组织结构的本项目不虚构部门/下属数据域。

client 权限固定为 self；admin 权限按管理服务返回 platform_metadata，用户账号管理可操作其允许的目标账号集合。多角色不能把“读全部元数据”和“修改本人数据”拼成“修改全部数据”；每个动作分别求解匹配授权与范围。申请者的 grantable_role_ids/permission 上限和受保护目标限制也是服务端校验条件，不接受客户端自报范围。

## 4. 登录、注册与会话

推荐用户端 /login、管理端 /admin/login；认证API按固定路由确定audience，客户端header不能决定授权。两端同一个User有独立会话；用户端凭据不用于/admin API，首版切换入口重新登录。Web opaque Cookie与原生轮换协议以 [账号流程](../features/ACCOUNT_FLOWS.md) 为准。

- 注册由服务器按当前注册策略创建账号、私有 Library 和默认角色。请求中出现 role/status/is_admin/permissions 等敏感字段拒绝；默认注册角色只能从可公开分配的 client 角色中选择，不能配置为管理角色。
- 账号建议区分 pending、active、disabled，以及带到期时间的安全锁定。只有 active 且拥有对应 login 权限的账号能建立/续期该端会话；pending 显示待审批，禁用或撤销登录资格拒绝新登录与刷新。
- 账号禁用/强制下线撤销受影响会话；移除 client.login 只撤销学习端会话，移除 admin.login 撤销管理端会话；全账号禁用两端一起处理。
- 通用失败响应避免暴露账号或角色细节；管理审计记录安全的真实原因分类。找回密码/注销当前会话不因功能菜单被撤销而消失，按专用身份与频率规则执行。
- 管理 Web 使用独立名称、受众与路径约束的 Cookie/CSRF 配置，保持 HTTPS/HttpOnly/SameSite；不能只依赖 Cookie Path 作为权限边界。

仅有角色配置但没有两端登录权限时，不生成可访问业务的会话。拥有登录资格却没有可用业务页面时，显示受控空状态与自身账号/退出入口，不能默认落到无权查看的书库或管理首页。

## 5. 两端页面、菜单和按钮

服务端提供当前受众的权限快照及已过滤导航，例如GET /api/v1/me/access和GET /api/v1/admin/me/access。返回最小本人身份user_id、instance_id、audience、不可作为凭据的session_ref，以及account_status、由user_authz_version+policy_revision组成的authz_version、有效权限/范围摘要、feature_flags、navigation；不返回其他用户策略或凭据。无需profile.read就能绑定当前会话与缓存，完整资料/设置另按其权限可选加载。菜单/安全配置变化同样推进policy_revision。前端不把快照作为向后端发出授权决定的凭证。

MenuItem 包含固定 key、surface、parent_key、route_key、component_key、标题、图标、顺序、enabled 和 required_permissions/all_or_any。页面组件与路由来自 Flutter 发布清单；只允许显示/布局配置，更新菜单不能创造新接口权限。父菜单只在有可见子项时显示。

页面/动作的最低权限要求由代码注册，菜单配置只能追加显示限制，不能用空权限或 any 条件降低页面本身的要求。权限依赖和范围由服务端解析成有效快照，前端只消费结果，不另行实现一套角色继承算法。

- Riverpod 保存当前账号/受众/版本的 AccessSnapshot；go_router 在权限加载后匹配允许的路由，加载期间不先渲染受限页面。
- 菜单可见性由功能开关、页面所需权限与平台支持共同决定；按钮依据具体动作，读写权限分离；无权操作默认隐藏，业务暂不可用可禁用并给原因。
- 深链接、浏览器刷新、前进/后退、直接粘贴地址和新窗口均走路由守卫；拒绝时展示无权限页或跳转首个可访问页，不自动请求敏感数据。
- 表格字段、编辑表单、批量按钮和导出也走权限控制。管理 API 使用不同 DTO 裁剪字段，不能把隐藏列数据全部发给前端。
- 菜单 enabled=false 只管理导航显示；若要停用功能访问，必须修改对应权限/feature flag 并由后端执行。页面访问权限与菜单装饰开关在管理 UI 分开命名，避免“隐藏”被误认为“撤权”。
- 权限快照失败或版本不明时不放行受限页面；权限变更后退出失权页面、取消订阅/清空对应内存状态，换账号或受众不得复用旧快照。

两端使用相同权限代码和判断规则，Flutter 不再通过 role == admin 或本地手改布尔值决定访问。客户端代码包存在某个组件不代表该用户被授权使用它。

## 6. FastAPI、Worker 与策略存储

推荐后端封装 AuthorizationService，PyCasbin 负责角色与策略匹配。PyCasbin 官方提供 RBAC/角色关系和异步策略加载入口，但不负责账号是否真实存在、业务归属、菜单生成或数据库事务；这些由 Haruka 实现。参考 [PyCasbin](https://github.com/apache/casbin-pycasbin) 和 [Casbin RBAC](https://casbin.apache.org/docs/rbac/)。具体依赖与 matcher/effect 在阶段 1 验证后锁定，当前为推荐选型。

~~~mermaid
flowchart LR
    C[Flutter 用户端 / 管理端] --> A[认证：身份 / 受众 / 会话]
    A --> V[当前账号状态与权限版本]
    V --> R[AuthorizationService / PyCasbin]
    R --> S[业务服务：归属 / 范围 / 状态]
    S --> D[PostgreSQL / MinIO / Job]
    R --> U[权限快照 / 导航 / 动作]
    U --> C
~~~

### 数据模型与单一事实来源

| 对象 | 职责 |
| --- | --- |
| User / AuthSession | PG账号状态/authz_version、安全epoch及会话受众/撤销/绝对期限；Redis不是持久撤销的唯一来源 |
| Role / PermissionCatalog | 角色 code/状态/保护标记；代码注册的权限、所属受众、支持的数据范围与依赖 |
| UserRole / RoleInheritance | 用户多角色与有向无环继承关系，唯一约束与引用校验 |
| RolePermission | 角色、权限、allow/deny、合法 data_scope 的授权项 |
| RoleGrantBoundary | 哪些角色/权限允许由哪个管理授权范围分配，受保护目标规则 |
| MenuItem / MenuPermission | 两端导航元数据和明确 all/any 的可见条件 |
| AuthorizationRevision | 全局策略 revision，角色/权限/继承/功能安全配置改变时事务性递增 |
| AdminAuditEvent / OutboxEvent | 管理变更的操作者、对象、权限差异、安全摘要、结果及向日志平台发送的事件 |

上述关系表为权威来源，应用在一致的数据库快照上生成版本化 Casbin p/g 策略与前端权限快照。不要同时维护可独立修改的 RolePermission 和另一份 casbin_rule 授权表。首版推荐只读加载适配器/投影，所有授权变更经业务事务；不调用 Casbin AutoSave 在事务外另写一套权限。

策略主体使用 user::UUID、role::UUID 命名区分；surface 与 data_scope 由路由和服务端受信任数据构造，不能取请求体的 is_admin/user_id/scope。PyCasbin 只匹配操作授权；数据库行过滤由仓储执行，返回对象再检查关联与字段范围。

### 每个执行入口都检查

FastAPI 对所有受保护路由要求显式声明所需权限，公共注册/登录/健康/受限匿名日志入口单独登记。认证基础能力也单独登记：本人访问快照和已登录遥测要求当前受众的 login 权限；密码找回、本人改密/退出按专用身份验证、会话与频率规则处理，不能因功能菜单撤销而无法退出。上述例外不授予其他业务动作或日志查询权。认证中间件 + 授权依赖覆盖 HTTP、下载、上传签名、SSE、批量接口；CI 扫描未声明保护或错误公开的业务路由。

服务层再次执行资源归属和业务状态约束，防止 Worker/Agent 绕过路由。调用管理接口需要 admin 受众及对应 admin 权限，用户端和管理端权限不能互相替代。身份失效通常为 401、动作无权为 403、他人私有对象维持统一不可访问结果；前端按错误类型清理状态而非无限刷新令牌。

后台 Job 保留 actor_user_id、owner_user_id、发起受众、required_permission_codes 和操作上下文引用，不能携带可任意扩权的权限快照作为凭证。Worker 开始、每个新的付费步骤、Agent 工具操作和最终业务提交前重新检查当前账号/权限与所有权。已撤权的 queued Job 不继续调用模型；在途供应商请求无法保证撤销收费，停止后续步骤并记录状态。

后台执行以已受理 Job 的授权操作记录和当前账号/动作权限为依据，不要求发起时的浏览器会话始终在线。关闭页面、普通退出或单独撤销设备会话不自动取消已提交任务；禁用账号、撤销相应权限或取消任务才停止后续受限执行，任务不能持有登录 Token 续命。

已保存学习数据和答卷不因撤权而删除。服务端截止封存、取消清理、已返回产物的最小落库可用固定系统主体执行，动作白名单只允许维护既有状态，不获得浏览私有内容或发起新付费调用的通用权限；操作仍记录原所有者/发起者。考试失去作答/批改权限时保留答卷，按 [试卷模式](../features/EXAM_MODE.md) 的状态边界处理。

## 7. 权限更新与失效

权限修改在同一事务中提交角色/绑定/状态、用户或全局权限 revision、审计及 Outbox。界面操作成功的含义是事务已提交；不能先更新 UI 再异步尝试写真实权限。

为了明确撤权语义，首版推荐每个受保护请求从数据库检查账号状态、user_authz_version 和全局 AuthorizationRevision；Redis 仅缓存与这两个版本及受众严格绑定的策略/权限快照。发现新版本就加载一致快照，加载失败拒绝该操作，不回退旧授权。权限变更后开始的新请求因此受新策略约束，不能只等 JWT 过期或依赖会丢失的 Pub/Sub 消息。

Redis 发布失效通知供各实例和客户端加快刷新；不是唯一正确性机制。缓存键包含项目、用户、受众和 revision，worker/多 API 实例同样校验版本。后续优化数据库检查开销时必须重新定义并测试撤权窗口，不能静默改为长 TTL。

长连接/运行中任务在事件、工具、付费和提交边界重新检查；SSE 心跳也检查状态，推荐撤权后 5 秒内终止失权订阅并刷新 UI。对并发管理写操作使用预期 revision 与事务校验，冲突要求重新获取差异；撤销管理者权限后不能让其已打开的旧表单继续授权。授权变更与敏感管理写使用一致的 revision/账号行锁顺序或等价串行化条件，将授权检查保持到事务提交，避免“检查后被撤权仍提交”；已经完成的外部调用不承诺回滚。

离线设备无法收到即时撤权。用户端已有阅读/音频缓存只在有效的离线访问租期内可用（首版建议最多 24 小时，具体时长部署配置），并限定为缓存快照里已授予的只读能力；离线不能登录管理后台、管理权限、发起 AI/交卷或绕过服务器权限。重连先重新校验，失去登录/内容权限即清理相应缓存与状态；已下载文件无法被服务器物理收回，不能承诺瞬时离线撤权。

MinIO 预签名地址在签发时检查权限，但已签发地址在过期前可能仍有效；有效期需要限制并验收。需要请求时即时检查撤权的私有下载改走鉴权代理，不把短期签名 URL 等同于每次访问都会查询 RBAC，详见 [认证与文件边界](AUTH_AND_ISOLATION.md)。

## 8. 授权管理、初始化与审计

### 防止管理操作扩大自身权限

有 admin.user.role.assign 不等于能授予任何角色；有 admin.role.permission.assign 不等于能往角色添加任意权限。每次分配检查目标角色/权限的有效继承闭包、数据范围、显式拒绝与操作者的授予上限，不能通过先改角色再分配、修改默认注册角色、继承高权限角色等方式提升权限。

首版仅给 super_admin 模板授予 admin.grant_boundary.update 与 admin.protected_role.manage，服务端按这些权限及受保护目标约束维护授予上限和系统角色。受委派管理员只能管理明确授权的角色/账号范围，不能修改自身绑定或给自身升权；改变一个已分配角色时也要检查所有受影响账号。策略编辑先展示有效权限差异、影响人数及登录资格变化，再提交带 revision 的变更。

保护最后一个可登录的 super_admin：禁用、删除、移除角色、修改其角色权限/继承或登录策略均需在事务内检查，避免并发变更把系统锁死。角色停用/删除先展示影响；有引用时采用显式替换/迁移或拒绝，不能留下悬空绑定。

### 初始化与恢复

首个管理员由部署方的一次性初始化命令/受控部署流程创建，使用独立 Secret 输入、密码哈希并记审计；不是第一个公开注册的人自动成为管理员，也不提供默认账号/硬编码密码。角色与权限种子通过版本化迁移维护，后续部署幂等且不覆盖人工授权。

恢复管理员通过受控运维命令完成并审计，不能提供可匿名调用的“修复管理员”接口。管理敏感变更要求近期身份验证并记录操作者；这属于应用管理流程，当前文档任务不执行任何初始化或真实账号变更。

### 审计与统一日志

管理变更在业务事务内保存 AdminAuditEvent（应用接口不可修改/删除）并提交 Outbox，再转为 JSON 日志进入 MyHome 的 Alloy/Loki/Grafana。Loki 故障不回滚已经提交的权限事务，由 Outbox 补发；数据库审计写入失败则整笔管理修改失败。数据库层运维权限与审计留存单独管理，不把 Loki 当前 7 天留存当作完整授权历史。

记录 actor_user_id、受众、动作权限、目标类型/ID、变更前后权限差异或状态摘要、revision、request/operation_id、结果与原因分类。禁止密码、Token、Key、材料/答卷正文和完整敏感字段快照入审计或日志。登录拒绝、越权拒绝、角色/菜单/策略修改、会话撤销、管理员初始化均有对应事件，复用 [日志与埋点](../engineering/OBSERVABILITY.md)。
