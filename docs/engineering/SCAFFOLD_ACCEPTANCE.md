# 脚手架阶段验收与参考闭环

状态：设计基线 v0.1，2026-09-22，未实现、未执行。本文把 [实施计划阶段 1](../planning/ROADMAP.md) 拆成 B0/B1/B2 三个工程子里程碑，不改变产品 P0 范围，也不表示完成任一子里程碑就能公开发布。

包装、命令、构建身份和生成协议由 [脚手架蓝图](SCAFFOLD_BLUEPRINT.md) 定义；本文只定义应取得的行为与证据。测试层级、必需用例和覆盖率算法以 [测试规范](TESTING.md) 为准，CI、评审、制品和发布门禁以 [交付验收](DELIVERY_ACCEPTANCE.md) 为准，不维护第二套阈值或豁免机制。

**必须**按 B0 → B1 → B2 逐步交付，后续里程碑保留前序已交付能力。**推荐**以本文的真实业务闭环作为其他模块的参考实现，展示目录、依赖注入、事务、错误、日志与测试怎样配合。**例外**沿用交付规范的独立评审、责任人、期限和替代证据要求，不能通过修改阶段标签掩盖已承诺功能失败。

| --- | --- | --- |

允许缺席仅指未进入本里程碑、未承诺可用的功能。验收记录须列出具体功能及后续交付节点，不把它们记成测试 passed 或 skipped。未实现入口不显示为可用，能力目录和 API 不返回虚构成功。已经创建或暴露的代码仍须接受静态检查、源码覆盖清单和适用的安全/协议检查，不能因“业务以后交付”整体排除。

SCF 是本文稳定的验收 ID，进入未来 required_cases 清单后再关联具体测试节点与参数。每个里程碑记录适用 SCF、对应功能验收 ID、平台/传输/故障参数及证据；本次要求的项未收集、未实现、失败、仅 skip/xfail/deselect 或缺平台证据，均不能签署该里程碑通过。检查器、分片汇总与完整覆盖分母按测试规范执行，不以某一命令退出 0 代替结果。

B0 的配置拒绝、进程生命周期与契约处理是首批实际核心代码，应登记到核心组；以后新增认证、任务等核心模块时扩充清单。不能用“尚无全部业务”接受空核心清单，不能先铺满无测试的占位模块再从统计中删去。

实施时同时映射 [前端定位/E2E的UIE项](FRONTEND_E2E.md) 和 [测试数据的TDS项](TEST_DATA.md)：B0验证单源标识生成、最小Key/语义定位原型及素材/场景校验；B1验证真实登录/收藏的数据工厂、隔离与清理；B2增加异步Fake、竞争和迟到写入清理。已进入范围的项缺实现/结果要失败；其他业务素材与平台专属操作随对应功能交付。

## 2. B0：可重复工程基础

### 干净检出与制品启动

从干净检出开始，只使用已提交的非秘密配置模板、工具清单和锁文件，按蓝图的 doctor、bootstrap、codegen、check、dev 职责执行。具体命令语法以工程实际入口为准；当前这些是待实现合同。测试使用新虚拟环境和独立资源，不能借作者已有全局包、相邻 MyHome 目录或未记录的本地文件成功。

doctor 必须能区分缺工具、版本不符、缺服务、端口冲突与配置缺项；输出可采取的修复步骤和失败状态，不打印连接串/秘密。bootstrap 可重复执行且不覆盖用户已有配置、不更新依赖锁、不默认启动付费调用或初始化公开管理员。分别记录 Windows PowerShell 与选定 CI shell 的真实结果，不能用其中一个替代另一个。

构建依赖不能仅凭运行 uv.lock 或顶层 Hatchling 版本认定已锁定。按蓝图中 backend/pyproject.toml 的 tool.uv.build-constraint-dependencies 单一约定，核对实际 PEP 517 直接/传递构建依赖的精确版本与摘要。B0 用支持该配置的锁定 uv 和干净构建缓存验证本包 wheel/sdist/editable，以及本阶段批准的第三方源码构建；缺约束、缺 hash 或实际闭包漂移必须失败并保存报告。尚未批准的源码构建不能临时下载未约束构建器后继续，本文不新增另一套构建锁来源。

后端先构建候选 wheel，再在新的运行环境中按锁定运行依赖安装该 wheel；切换到仓库外目录，移除 checkout 挂载及指向它的 PYTHONPATH，核对模块实际来自安装位置。用正式 haruka-api、haruka-worker、haruka-outbox、haruka-manage 入口验证安装、配置校验与本阶段具备的启动能力，不能只有 help 能运行。尚无业务 handler 的 Worker/Outbox 在 B0 验证入口和生命周期，真实领取/投递在 B2 验证。迁移、种子、Prompt/协议等运行资源按蓝图随包或同版本部署附件交付，路径显式解析，不依赖当前工作目录或未打包的源码文件。

包安装和 console scripts 是分发层能力，不能仅靠源码目录内 import 证明。依据：[uv 构建与包安装验证](https://docs.astral.sh/uv/guides/package/)、[PyPA 入口规范](https://packaging.python.org/en/latest/specifications/entry-points/)。本验收不要求把包发布到公共仓库。

### 迁移、种子、组装与生成

迁移和种子由受控管理入口执行，API/Worker 普通启动不自动修改 schema。B0 在隔离 PostgreSQL 执行空库到当前 revision、重复启动和种子幂等检查；后续增加迁移时，补前一已交付 revision 的升级路径。权限/菜单种子与合成测试数据分开：生产初始化不装载测试账号/材料，重复种子不覆盖人工授权，首管理员初始化遵守 [RBAC](../architecture/ADMIN_AND_RBAC.md) 的受控方式。

迁移竞争采用蓝图的同一物理连接持锁并执行 Alembic 协议。必须用真实双迁移进程证明只有持锁者可执行 DDL，等待/超时者不并行升级；持锁/DDL 连接中断时原执行失败，不透明另开连接续跑。重试须重新取得锁并在锁内核对实际 revision/已提交 schema，再决定继续或要求修复；不能只把首次计划的 revision 当作数据库现状。故障注入覆盖取锁后、DDL 中以及部分步骤已提交后的中断，证据记录实际锁等待、连接/进程结果和最终 schema。

进程资源在统一组装入口创建和关闭。模块导入、读取命令帮助及 schema 导出不偷偷连接数据库或供应商；配置错误在接收业务前失败；中途初始化失败释放已取得资源。API lifespan 和独立 Worker/Outbox 停止都要有有界等待与实际关闭断言，不以进程被强杀掩盖连接泄漏。FastAPI 生命周期能力依据 [官方 lifespan 说明](https://fastapi.tiangolo.com/advanced/events/)。

codegen 按蓝图的权威来源生成 OpenAPI/Dart 契约和已采用的目录/常量，不建立互相反向生成的多份主表。干净检出生成后与提交的生成物一致，再次生成无差异；仅包含真实生成物的忽略目录按清单核对。用修改源字段、删除一个生成文件、生成器版本不符、写入未登记权限/事件等坏样本证明检查会失败。生成器尚处于原型评估时可按蓝图使用集中手写 DTO，但不能跳过 OpenAPI 样本解码与兼容差异检查，记录哪些输出尚非自动生成。

## 3. B1：三端登录与收藏参考闭环

### 合成数据与正常路径

用受控 dev/test seed 建立 A/B 两个独立用户、私有 Library、最小授权角色、login-only 账号及最小管理登录账号。使用一次性本地测试秘密，不提交可公开复用的密码。种子只准备前置对象，不代替要验收的业务操作，也不作为公开注册入口。

为 A/B 分别预置一份自建英/日短材料、不可变内容版本和有效选区，记录 fixture 版本和许可。B1 只需显示该合成片段并从真实选区创建收藏，不要求先实现完整上传、解析或阅读器；不得虚构 manual 来源类型、伪造稳定 ID，或为了演示新增生产调试 API。

1. 用户在 Windows、Web、Android 分别经正式登录接口取得对应会话，再取 me/access 绑定当前实例、账号、受众与会话；加载/失败/无权状态有明确界面。profile/settings 无权时不阻止 login-only 空状态和退出入口。
2. A 打开获授权的合成来源片段，选择内容并通过真实 POST collections 保存一条单词收藏。服务端核对来源、权限、所有者与幂等后提交，前端仅在确认提交后显示成功。
3. 经真实 GET collections 查询并渲染结果，重启/刷新客户端仍能读到同一 ID；同一账号另一平台可见服务器结果，B 的列表为空或仅含 B 自己的条目。
4. 注入超时和重复提交，同一幂等键只得到一条业务记录；伪造 owner/source/tag ID、撤销 create/read、旧会话或错误受众请求不能绕过对应约束。
5. A 退出切换 B，停止旧请求/订阅并清理 A 的私有状态；故意让 A 的响应和日志队列迟到，不能进入 B 的列表、缓存或已登录日志归属。
6. 管理 Web 用正式 admin 登录/access 获得最小受控页面；验证 client 会话不能进入管理接口，管理身份不能绕过收藏本人范围。此处不宣称完整管理后台已完成。

注册开放、邮箱验证、找回方式仍按 [决策清单](../planning/DECISIONS_AND_ASSUMPTIONS.md) 锁定。预置 active 测试账号只为验证登录，不证明真实注册/激活/恢复可用；未实现的入口不伪装成可用。会话行为直接遵守 [账号流程](../features/ACCOUNT_FLOWS.md)，不另立“脚手架简化认证”。

### 日志和失败证据

B1 的正常/info 埋点、登录/拒绝/退出、收藏提交、API 与 ORM 结果、相关 PG 引擎样本须在隔离采集环境或已获授权的集成采集环境进入 Alloy/Loki，并取得 Grafana 可查询证据。按 [观测规范](OBSERVABILITY.md) 关联客户端 operation、API request 与数据库连接线索；stdout 截图不能代替已要求的接收/查询路径。正式共享 MyHome 接入、全部业务来源和容量留存仍有独立交付验收，不因本闭环通过全部勾选。

注入假秘密与材料/笔记哨兵，验证日志和报告未泄漏；停止日志接收后业务行为符合观测契约，队列有界、不会递归放大；恢复后补传遵守原账号/受众。服务端提交事实与前端点击事件分别验证，不能靠“看到 collection.saved”推断数据库已写入。

| ID | 必须证明 | 平台/最低证据与故障样本 |
| --- | --- | --- |
| SCF-B1-01 | 合成账号正式登录/access、会话恢复与退出成立；login-only 可启动 | 用户三端 + 管理 Web；对应会话/受众、错误密码、失效/撤销、PG/Redis 故障及无 profile/settings 权限证据 |
| SCF-B1-02 | 本人有效选区创建收藏并持久读取，三端使用同一契约 | 用户三端；正式 API、真实 PG、Dart DTO/状态与界面记录；重启和另一平台读取不依赖内存 fixture |
| SCF-B1-03 | 创建/查询权限、所有者、来源、幂等与错误状态一致 | API/真实 DB + 组件/三端主路径；A/B ID 替换、deny、同键重复、提交已完成但响应丢失均有断言 |
| SCF-B1-04 | 退出换账号及 client/admin 切换不串状态或日志 | 用户三端 + 管理 Web；迟到响应、离线队列、浏览器多标签、原生重启恢复和旧凭据请求 |

## 4. B2：Fake 模型与真实持久任务

### 唯一替换边界

B2 推荐使用现有“从收藏生成普通练习”业务：在 B1 收藏中明确选择一项，要求生成一道受支持题型，通过正式 POST practice-generations 受理。权限、来源、Key 状态、预算、Job/AiRun 和业务结果均使用正式服务；schema 与路径以 [API 契约](../architecture/API_CONTRACTS.md) 和 [收藏与练习](../features/COLLECTIONS_AND_PRACTICE.md) 为准，不创建仅供生产调试的 fake-job/run-model HTTP 路由。

只在 dev/test 的受控组装配置中注入 Pydantic AI 测试模型或确定性供应商替身；用户请求体、Header、model ID、管理模型目录都不能自行切换 Fake。其他环境（包括 staging/production）必须拒绝 Fake 配置和测试 seed，验证 API 与独立 Worker 各入口均拒绝，不能只在 Flutter 隐藏按钮。缺少正式 Key 时也不能自动使用 Fake。

合成用户的凭据记录使用无法访问外部服务的测试哨兵，仍走正常的凭据所有者/状态/代次与预算校验；同时保留“缺凭据”“凭据撤销”的失败用例。Fake 仅替换供应商边界，不把 AuthorizationService、PG、Redis、Kafka、Job/Outbox/Worker 或 SSE 替换成内存成功桩。运行记录和日志按注册字段标识 dev/test 模拟执行，模拟用量不能冒充真实供应商用量、费用或质量证据。

Pydantic AI 的 TestModel/FunctionModel、Agent.override 与禁用真实模型请求的能力见 [官方测试说明](https://pydantic.dev/docs/ai/guides/testing/)。除此之外仍按测试规范限制独立 HTTP/供应商出站；使用 Fake 不代表所有联网适配器自动被拦截。只有声明的隔离基础设施可访问，未声明供应商请求直接使验收失败。

### 正常任务闭环

1. API 验证当前用户、来源、明确出题意图和配置，事务创建业务生成请求、Job/AiRun、Outbox；持久受理后返回任务/运行引用。
2. 正式 Outbox 进程发布到隔离 Kafka，正式 Worker 领取、核对当前权限/凭据/预算并调用 Fake；Fake 返回已版本化的有效题目样本。
3. Pydantic 与业务校验检查结构、来源和归属，Worker 以当前租约/代次提交结果及状态；客户端按正式权限查询生成结果。
4. 用户三端订阅正式 runs/{id}/events，看到受理/进度/完成或失败，完成结果从持久资源读取。界面断连后通过事件游标/运行快照恢复，不重新 POST 一次生成操作。
5. 查询 PG 业务记录、Job/阶段、Outbox 和模拟调用次数，证明完成与去重；沿 operation/request/job/ai_run 关联到 API、Outbox、Worker、模型适配与前端日志。

SSE 进度可以使用应用事件，不要求 Fake 伪造逐 token 流。参考闭环只证明这一条题目生成通道与任务骨架，不声称多轮 Agent、所有工具、评分质量或 TTS 已通过。题目 DTO 仍遵守原有题面/答案隔离规则，不能因为是测试样本就给普通出题等待页面泄露不应返回的答案字段。

### 故障、恢复与撤权

使用确定性屏障、测试时钟、进程控制及替身响应注入故障，不向生产加入任意“崩溃/跳权/改状态”接口。重试、unknown、取消与租约语义严格沿用 [数据与任务](../architecture/DATA_AND_JOBS.md)，不能为方便 demo 将全部失败自动重新跑一遍。

| ID | 必须证明 | 平台/最低证据与故障样本 |
| --- | --- | --- |
| SCF-B2-01 | B1 收藏经真实持久链路生成有效结果，三端可查询 | 后端真实进程/PG/Redis/Kafka + 用户三端；受理/提交记录、Fake 次数、结果引用、相同版本日志 |
| SCF-B2-02 | Fake 只能受控注入且无真实模型出站 | API/Worker 配置与网络测试；正式环境、用户自报 Fake、测试 seed、缺 Key、误调用独立 HTTP 都不能悄悄通过 |
| SCF-B2-03 | 持久受理和重复投递不丢事实、不重复业务结果 | 真实进程/数据库；提交前后故障、Kafka 不可用再恢复、发送成功但 Outbox 未标记、消费者提交后未确认 |
| SCF-B2-04 | 中断恢复从已提交阶段继续，旧 Worker 不能覆盖新结果 | 真实 Worker/租约；停进程、到期接管、旧租约迟到、同幂等键重复请求；不重置整个 Job 无界调用 |
| SCF-B2-05 | 撤权、删 Key、来源失效或取消后不开始新的受限步骤 | 后端并发测试 + 三端状态展示；提交前重查，返回产物按封存规则处理，A/B 任务/SSE/结果不可互读 |
| SCF-B2-06 | 无效输出/来源、预算耗尽与 unknown 有确定结果 | Fake schema 错误、伪造来源、限流、调用中断；不得把失败标成功，unknown 不自动再发付费 attempt |
| SCF-B2-07 | SSE 断连/回放窗口外可查最终状态且不重复生成 | 用户三端；代理与客户端实际断连、重连重新授权、窗口外快照恢复、账号切换关闭旧订阅 |
| SCF-B2-08 | 模型/任务正常与失败日志完整、脱敏且模拟口径可辨 | API/Outbox/Worker/Fake/ORM/前端至查询平台；无 Prompt/题目/Key/工具正文，次数/用量无重复累计 |

后端竞态故障不要求在三端重复执行相同数据库测试；每个必须的平台体验与每个后端故障执行键分别登记，不能用一端 UI 通过代替另一端，也不能用单测替代真实 Worker/Kafka 证据。

## 5. CI 与里程碑证据

CI 沿用交付规范的顺序与门禁，新增的是明确 B0/B1/B2 选择范围：本次里程碑的 SCF、前序已交付回归、相关业务用例和检查器坏样本共同组成必需集合。只运行局部 check 可以用于开发反馈，但报告必须标局部；缺少本阶段依赖/设备/分片是未完成验收，不能通过 skip 或缩小清单转成通过。

| 证据 | 最小内容 |
| --- | --- |
| 范围 | 里程碑、SCF/业务用例映射、允许未交付功能及下阶段、锁定后的本次平台/参数矩阵 |
| 来源 | 提交、工具/依赖/生成器版本、配置模式、fixture/seed/迁移 revision、无秘密的环境标识 |
| 制品 | wheel/应用制品摘要、运行依赖和资源清单、非 checkout 安装路径、三端实际构建与运行模式 |
| 执行 | 原始收集和机器报告、执行键结果、命令/退出码、覆盖率完整性、故障注入与恢复断言 |
| 闭环 | API/业务对象与 Job/run 引用、脱敏日志关联/查询证据、三端关键操作截图或记录 |
| 审查 | 独立 reviewer、问题与修订复核、仍待产品决定/实测的项目；只给已执行项通过结论 |

B0 可先使用各平台适合开发的构建模式验证壳；B1/B2 必须另有实际 release 构建在隔离 dev/test 服务上的核心路径烟测，记录构建模式与应用身份。这里的 release 指编译制品模式，不等于 production 服务配置，也不赋予对外发布授权；Fake 仍仅能由 dev/test 后端注入。正式签名分发、全部原生插件、完整平台矩阵和生产部署验收继续遵守交付规范。

完成 B2 仅表示阶段 1 的参考工程骨架可复用。阶段 1 剩余的账号/RBAC、管理、日志、供应商能力等验收，以及后续材料、考试、CSV、三端发布均保留各自未完成状态。当前本文全部条目为未来验收，未创建命令、配置、测试、账号或制品。
