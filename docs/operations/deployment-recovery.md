# 部署、迁移与恢复

状态：设计基线 v0.1，2026-09-22，尚未部署或演练。本篇是 Haruka 运行操作的唯一正文，承接配置与交付规范中的发布、故障、回滚和恢复步骤。配置项/健康定义见 [运行配置](configuration.md)，包与维护 CLI 的实现合同见 [脚手架](../engineering/scaffold.md)，发布证据和放行条件见 [交付验收](../delivery/acceptance.md)。

## 1. 操作前核对

本文不授权连接或修改 MyHome/生产服务。实施时先核对本次授权范围、目标环境和负责人；[MyHome 复用](myhome-integration.md) 的源码事实不能替代实际服务器核验。

- 确认 Haruka 独立数据库/账号、Bucket、Kafka topic/group、Redis 命名空间与 Secret；核对网络、TLS、公开 API/对象地址、版本和容量余量。
- 固定本次 release、源提交、制品摘要、配置 schema、迁移起止 revision 和种子版本；推广使用已验收的同一制品，不在生产重新解析依赖或临时构建。
- 明确受影响能力、停止推广条件、Worker 排空窗口、维护访问方式和回退/恢复责任人；确认备份、密钥版本及演练证据满足本次变更。
- 记录检查和执行结果的安全引用，不在命令参数、日志或报告中暴露连接串、管理员初始密码、Token 或加密材料。

后续步骤使用工程阶段实现的正式维护入口，本文不虚构尚不存在的部署脚本参数。共享 PG/Redis/Kafka/MinIO/Alloy/Loki/Grafana 由原运维责任方管理，Haruka 发布、重启和卸载不得停止或清空共享服务。

## 2. 首次部署与受控迁移

1. 准备隔离资源、类型化配置与独立 Secret，校验配置及必要网络连接，缺必需条件即停止，不采用默认密码或全局模型调用 Key。
2. 使用与应用同提交的迁移资源，经正式 haruka-manage 维护入口执行数据库检查和迁移。完整算法以 [脚手架的数据库初始化与种子](../engineering/scaffold.md#6-数据库初始化与种子) 为准：稳定数据库级迁移锁和 DDL 共用同一物理 PG 连接，锁内核对实际 revision；锁超时/连接中断失败，重试重新取得锁并核对实际 revision/部分 DDL，不能透明续跑或改用无锁连接。
3. 迁移成功后同步版本化权限/菜单目录和初始模板，再单独执行受控首管理员初始化。目录同步不覆盖人工授权、注册策略或用户角色绑定，新权限不自动扩大自定义角色；种子重复/中断按提交边界恢复，不先清表。
4. 初始化只通过独立秘密输入、密码哈希、审计和已设计的管理保护流程；不是第一个公开注册者自动成为管理员，不创建匿名修复接口。开发测试 seed/Fake 只允许 dev/test，不能混入生产初始化。
5. 启动 Haruka API、Worker、Outbox 与 Web，检查 schema 兼容、健康和日志；以合成 learner/admin 分别完成被本次范围承诺的登录、权限隔离与最小业务探针。

API、Worker、Outbox 只检查 schema 兼容，不在各实例启动时自动迁移。每个迁移必须声明可逆性、数据损失风险、锁/耗时和恢复前提；迁移失败停止推广并核对已提交步骤，不以命令重跑代替状态检查，更不得因迁移重试触发外部模型调用。

## 3. 常规发布

1. 完成操作前核对，记录当前应用/配置/schema 及恢复点；验证备份可用和恢复演练记录，暂停与迁移冲突的调度并留出 Worker 排空窗口。
2. 单个受控维护任务执行经审核的向后兼容变更，按上一节的同连接迁移协议处理并发与失败。
3. 按兼容协议发布后端、Worker、Outbox，执行健康和小范围业务探针；再发布 Web 静态制品并分发原生包，按灰度或小批切换结果决定是否扩大。
4. 验证新旧客户端并存、未完成 Job/Outbox、client/admin 会话和授权种子兼容；最低客户端版本、Web 入口缓存和资源路由按配置合同处理。
5. 核对前端/后台、AI/TTS、数据库及基础设施的采集来源，确认成功/info 事件、审计投递与 release 关联可查；验证共享 MyHome 原有业务和查询没有退化。
6. 满足交付门禁并稳定观察后才扩大；不兼容的字段删除/收缩另行安排，不能在同次滚动发布中先删除旧代码仍依赖的字段。

发现越权、数据损坏、持续关键失败或采集缺口等异常，按已登记条件停止推广，保留当前制品/配置/任务状态证据后进入故障或回退流程。通过构建、单次健康响应或进程启动不能替代发布验收。

## 4. 停机与任务处理

先停止本次需要暂停的新受理/调度与 Worker 新领取，再按有界窗口处理在途阶段；API/Worker/Outbox 的实际关闭与资源释放遵循 [脚手架](../engineering/scaffold.md)。保存任务、租约、代次和外部调用的已知/unknown 状态后关闭连接，不依赖 API 进程内后台线程完成持久业务。

租约到期后由符合当前权限的 Worker 按已提交阶段恢复，fence 阻止旧 Worker 迟到提交。强制退出不证明供应商未执行或用量为零；unknown 结果、取消、撤权和供应商调用重试统一按 [数据与任务](../architecture/data-jobs.md) 处理，不能从头无条件重跑或增加用户未授权上限。普通退出登录同样不是取消已提交 Job 的操作。

## 5. 故障处理

| 场景 | 处理顺序 | 恢复核对 |
| --- | --- | --- |
| PostgreSQL 不可用 | 停止身份判定与业务写入，客户端仅保留既有离线授权边界；恢复主库并检查实际 schema | 新请求重新验证身份/权限，已提交业务、Outbox 与幂等记录可核对，不使用滞后副本绕过撤销 |
| Redis 丢失 | 认证失败关闭并要求重新登录，重建非权威缓存；不以旧 JWT/快照跳过 PG | 持久撤销仍生效，业务数据保持；新会话按完整协议建立 |
| Kafka / Worker 故障 | 保留 Outbox 和可见 Job 状态，检查积压/租约；恢复消费者后按阶段继续 | 重投不重复提交，旧 Worker 迟到被 fence 拒绝，unknown 供应商调用不盲重跑 |
| MinIO 故障 | 读媒体/导入能力明确报错，未完成对象不发布；恢复后核对对象与数据库引用 | 不将缺对象当完整结果；GC 不删除仍被业务或在途任务使用的对象 |
| Loki / Alloy 故障 | 使用本地 Docker 日志及平台外探针定位，保留积压/缺口计数；恢复投递 | 审计 Outbox 按 event_id 可追溯，日志丢弃/延迟如实记录，不承诺普通日志零丢失 |
| 管理锁出 | 由受控运维身份使用既定恢复命令，保存审计，再重新登录与核对权限 | 无匿名恢复接口、默认密码或普通账号提权旁路；最后管理员与授予边界仍成立 |

健康/降级定义在 [配置](configuration.md)，日志与审计投递语义在 [观测](observability.md)，具体 Job/对象事务在数据契约；本表只维护运维动作，不另定义状态机。

## 6. 应用回滚与数据恢复

### 应用回滚

停止新受理高影响任务，核对当前迁移与上一制品/配置的兼容范围，然后切回已知摘要的旧制品并重新完成健康、会话、权限和任务检查，再恢复消费。数据库不自动 downgrade，也不能为了“回滚成功”执行破坏性降级。

若 schema 或数据已不兼容旧应用，选择经审核的修复性前滚或已演练的数据恢复方案。操作前明确可能丢失的数据窗口、在途外部调用和恢复点；恢复不是重放任意供应商调用步骤的许可。

### 备份与恢复演练

用户侧备份仍只有单词 CSV。运维另行保护 Haruka PostgreSQL、私有对象与部署加密材料；日志和元数据不能代替业务备份。保护范围、保留、负责人及 RPO/RTO 的配置归 [运行配置](configuration.md)，尚未验证的目标不能宣称达成。

1. 清点恢复点、数据库 revision、对象版本/引用与所需 encryption_key_version，检查备份可读、材料齐备和对应制品兼容；缺配对密钥时不能用其他 Key 假装解密成功。
2. 在隔离目标恢复并保持入口/消费者受控，先校验 schema、对象引用、密文可解和权限/审计完整性；不让历史任务在核对前自动产生新调用。
3. 恢复后的 AuthSession/安全 epoch 必须推进或撤销，并清理失效会话材料，防止历史快照复活旧会话；按 [认证](../architecture/authentication.md) 验证旧凭据拒绝与重新登录。
4. 核对 Job/Outbox/Inbox、有效成绩与学习贡献、对象回收状态和幂等边界；恢复点外的外部调用可能已经执行，按 unknown 策略核对，不能把回退后的记录缺失当“尚未发起供应商调用”。
5. 在受控环境完成账号隔离、对象访问和最小业务/日志探针，记录实际数据窗口和耗时。满足本次恢复条件后才恢复入口与消费者，保存结果和未解决差异。

演练必须证明数据库、对象和加密版本能够配对；单独成功导入 SQL 不等于恢复验收。数据库管理审计与授权历史的留存独立于 Loki 窗口。

## 7. 部署加密主密钥轮换

1. 加入新的 encryption_key_version，保留仍需解密的旧在线版本；新写入使用新版本。
2. 有界重加密并核对对象数量、失败记录和新旧版本分布；仅变更部署加密版本，不改变用户 credential_version 或发起模型连接测试。
3. 在线旧密文核对清零后，可按计划移除旧在线解密版本；归档恢复密钥继续独立受控保存。
4. 只有依赖旧密钥的全部备份过期，或备份已重加密且恢复验证通过，才可销毁对应旧归档版本；不能因在线轮换成功就破坏历史恢复能力。

未知密钥版本失败关闭，不当明文读取，不回退公共/其他用户凭据。轮换清单和验证只记录版本/摘要及结果，不输出密钥或供应商明文 Key。

## 8. 运维验收

配置本身的 OPS-01 在 [运行配置](configuration.md) 定义；下列 ID 保留原有含义，具体报告格式与放行条件由 [交付验收](../delivery/acceptance.md) 维护。

| ID | 必须证明 |
| --- | --- |
| OPS-02 | 从干净隔离环境部署、迁移/种子和初始化管理员可完成，learner/admin 最小路径与日志可查，不泄密、不覆盖人工授权 |
| OPS-03 | 逐项故障演练反映真实健康/降级、任务与恢复状态，日志积压和缺口可查，unknown 调用不盲重试 |
| OPS-04 | 上一制品回滚与不兼容迁移的前向/恢复方案可执行，迁移争锁/中断与实际 revision 核对有证据 |
| OPS-05 | 数据库、私有对象和加密材料能配对恢复，旧会话失效、幂等/引用正确；密钥轮换后历史备份仍有可验证恢复路径 |
| OPS-06 | MyHome 原有运行和查询保持可用，实际资源余量/限额、共享责任边界在发布证据中记录 |

全部条目仍待工程与实际环境验证。本次没有连接服务器、执行迁移、轮换密钥、创建备份或运行恢复演练。
